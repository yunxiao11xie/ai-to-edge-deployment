# 版本矩阵、故障定位与回归测试

> 端侧部署最危险的不是报错，而是“偶尔能跑，所以误以为版本和链路正确”。本文把问题从经验试错变成证据化定位。

## 1. 为什么必须保存版本矩阵

`.rkllm` 是面向目标平台构建的部署制品，运行依赖 Runtime、C API/ABI 和驱动。至少记录：

```yaml
experiment_id: 2026-xx-xx-qwen35-w4a16-001
host_os: Ubuntu_22.04.5_x86_64
python: 3.10.12
model_repo: Qwen/Qwen3.5-2B
model_revision: TODO_commit_hash
processor_revision: TODO_commit_hash
toolkit_version: 1.3.0
toolkit_wheel_sha256: TODO
export_script_sha256: TODO
quant: W4A16_GRQ
target: rk3576
num_npu_core: 2
max_context_export: 4096
artifact_sha256: TODO
board_os: KickPi_Ubuntu_24.04.3_aarch64
kernel: TODO_uname_r
npu_driver: 0.9.7
runtime_version: 1.3.0
librkllmrt_sha256: TODO
rkllm_header_revision: TODO
demo_binary_sha256: TODO
```

版本号相同也不够：本地源码 commit、wheel 文件、动态库和模型制品都应保存哈希，避免“同名文件被替换”。

## 2. 建立最小证据包

每次成功或失败都保存：

```text
evidence/<experiment_id>/
├─ manifest.yaml
├─ export_command.txt
├─ export.log
├─ board_env.txt
├─ runtime.log
├─ memory.csv
├─ temperature.csv
├─ result.jsonl
└─ hashes.sha256
```

`board_env.txt` 可包含系统、内核、驱动、动态库解析、CPU/内存/存储状态，但不要把账号、Token、代理密码写入证据包。

## 3. 按阶段定位，而不是按错误文字猜

```text
模型下载/配置
   ↓
Host 加载
   ↓
量化校准与 Build
   ↓
Export `.rkllm`
   ↓
传输与哈希
   ↓
动态库加载
   ↓
rkllm_init
   ↓
Prefill
   ↓
Decode/Callback
   ↓
服务/UI
```

先问“最后一个被证明确认成功的阶段是什么”，再检查下一个边界。

## 4. 故障树

### 4.1 Host 无法加载模型

检查：

- 模型文件是否完整，Git LFS 指针是否被误当权重；
- Model revision 与 Toolkit 支持范围；
- Python/Toolkit wheel 架构与版本；
- 自定义模型代码和 Processor 是否来自同一 revision；
- 8GB Host 是否因内存不足进入长时间换页。

### 4.2 量化或导出失败

检查：

- calibration manifest 路径、样本数量和实际文件；
- 输入是文本 token 还是 `inputs_embeds`；
- `target_platform`、量化 dtype/algorithm 的组合是否支持；
- 磁盘空间和 swap；
- 失败发生于 load、optimize、quantize 还是 export；
- 输出文件存在不代表成功，必须检查返回值、日志终态和文件哈希。

### 4.3 板端动态库无法加载

```bash
file ./llm_demo
file ./lib/librkllmrt.so
ldd ./llm_demo
```

确认 aarch64、依赖可解析、`LD_LIBRARY_PATH` 指向预期目录。不要让系统中另一份同名库被悄悄加载；必要时记录动态加载路径。

### 4.4 `rkllm_init` 失败

按顺序排查：

1. 制品 SHA-256 是否与 Host 一致；
2. `target_platform` 是否确为 RK3576；
3. Toolkit/Runtime/Header 是否配套；
4. NPU 驱动是否加载且版本已记录；
5. 可用内存、CMA 和 swap；
6. 参数结构是否由同版本默认函数初始化，保留字段是否被错误填充；
7. 用官方 Demo + 官方动态库复现，隔离自己的封装。

### 4.5 初始化成功但无输出/乱码

检查：

- Chat Template 和特殊 token；
- Tokenizer revision；
- 输入长度是否为 token 数而不是字符数；
- Callback 数据边界与 UTF-8 拼接；
- 状态机是否错误忽略 NORMAL/WAITING/FINISH；
- 是否在 Callback 返回了不符合头文件约定的值；
- 量化前 PC 参考、转换后板端结果是否使用同一 Prompt。

### 4.6 输出正确但很慢

先拆为 Tokenizer、Prefill、Decode、Render；再检查：

- 是否第一次冷启动；
- Prompt/历史是否意外增长；
- NPU 频率、温度和系统负载；
- 摄像头/桌面是否争用内存带宽；
- 是否发生 swap；
- 实际是否加载了期望的 W4A16 制品；
- 日志和网络发送是否阻塞 Callback。

### 4.7 运行一段时间后崩溃

检查：

- 每轮 PSS、线程数、文件描述符和 dma-buf 是否增长；
- 取消与回调竞态；
- RequestContext 是否在回调结束前释放；
- Qt 页面销毁后信号是否仍送达；
- 历史/文本/图像队列是否无界；
- 温度、供电和内核日志；
- 以最小官方 Demo 做同样循环，区分 Runtime 与应用问题。

## 5. 日志等级与观测

板端基线可设置：

```bash
export RKLLM_LOG_LEVEL=1
```

具体等级和输出随版本变化，以当前 README/Runtime 为准。日志至少要关联：

- request_id；
- 模型与 artifact hash；
- Prompt/生成 token 数；
- Prefill/Decode/总耗时；
- 终态与错误码；
- PSS、MemAvailable、CMA、swap；
- 温度和频率采样。

日志时间必须使用单调时钟计算耗时；墙上时间用于跨进程事件关联。

## 6. 回归测试分层

### 6.1 制品测试

- `.rkllm` 文件存在、大小合理、SHA-256 固定；
- manifest 所列版本齐全；
- 在目标板官方 Demo 能初始化；
- 固定 Prompt 能生成非空、有效 UTF-8 输出。

### 6.2 质量测试

- 中英文基础问答；
- 数字、代码、JSON 和指令遵循；
- 长文本摘要；
- 多轮历史；
- 量化敏感样本；
- 多模态物体、OCR、计数与负样本。

生成式模型不宜只做全文字符串相等。可使用结构化断言、关键事实、正则、JSON Schema、长度和人工抽检。

### 6.3 API 测试

- 非流式/流式；
- 空消息、超长消息、非法参数；
- 中止、客户端断开、超时；
- 连续请求和排队；
- 服务重启；
- `/health` 在 Loading/Ready/Running/Error 的状态正确。

### 6.4 性能与稳定性

- 固定基准的 TTFT、Prefill、Decode 不超过约定回退阈值；
- 报告 p50/p95，而不只看一次最快值；
- 100 轮内存不单调增长；
- 1 小时运行无 OOM、无持续换页、无不可恢复错误；
- Qt + IMX415 + RKNN + RKLLM 的完整场景单独设门槛。

## 7. 失败注入

主动测试以下情况：

1. 模型路径不存在；
2. 制品被截断或哈希错误；
3. 动态库不匹配；
4. 请求超过最大上下文；
5. 生成中客户端断开；
6. 连续快速点击停止/发送；
7. 摄像头拔出或帧超时；
8. 磁盘接近写满；
9. 低内存压力；
10. 服务进程被杀后重启。

目标不是“永不报错”，而是错误可识别、可恢复、不损坏后续状态。

## 8. 升级流程

Toolkit、Runtime 或驱动升级时：

1. 复制而不是覆盖旧环境；
2. 建立新版本矩阵；
3. 重新导出独立命名的制品；
4. 官方 Demo 最小验证；
5. 质量、API、性能、稳定性全量回归；
6. 比较报告后再切换默认版本；
7. 保留可回滚的旧动态库、应用和模型。

不要只替换 `librkllmrt.so` 后继续使用无法追溯的旧 `.rkllm`。

## 9. 验收标准

- 任一结果都能还原完整版本矩阵；
- 故障能被定位到明确阶段和契约边界；
- 官方 Demo 与自研应用之间有隔离实验；
- 每次升级都有自动化回归报告；
- 性能回退、内存增长和多模态错误均有门槛；
- 失败时能够安全回滚。

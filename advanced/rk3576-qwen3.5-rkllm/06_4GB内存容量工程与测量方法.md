# 4GB 内存容量工程与测量方法

> 对 4GB RK3576 来说，真正的问题不是“模型文件能不能放进 32GB eMMC”，而是 **Ubuntu Desktop、Qt、RKLLM、RKNN、摄像头缓冲区同时运行时，物理内存是否仍有稳定余量**。

## 1. 容量模型

整机峰值可以先写成：

\[
M_{total}=M_{OS}+M_{desktop}+M_{Qt}+M_{LLM}+M_{vision}+M_{camera}+M_{cache}+M_{margin}
\]

其中 LLM 又包含：

\[
M_{LLM}=M_{weights}+M_{runtime}+M_{state}+M_{KV}+M_{tokenizer}+M_{buffers}
\]

真正需要管理的是这些组件**时间上的重叠峰值**。单独启动每个模块都成功，不代表同时启动不会 OOM。

## 2. 必须分清的内存指标

| 指标 | 含义 | 易错点 |
|---|---|---|
| `.rkllm` 文件大小 | eMMC 上的文件字节数 | 不等于常驻内存 |
| VIRT/VmSize | 进程虚拟地址空间 | 映射文件也会计入，通常不能表示物理占用 |
| RSS | 当前驻留物理页 | 共享页会在多个进程中重复统计 |
| PSS | 共享页按比例分摊后的驻留量 | 多进程场景更适合做容量预算 |
| USS | 进程独占页 | 杀掉该进程大致能释放的独占部分 |
| VmHWM | 进程历史 RSS 高水位 | 不等于 PSS 峰值 |
| `MemAvailable` | 内核估算的可安全分配内存 | 比 `MemFree` 更有意义 |
| page cache | Linux 文件页缓存 | 在压力下可回收，不能全部算“被吃掉” |
| CMA/DMA/NPU buffer | 设备连续内存或驱动分配 | 可能不完整出现在某一进程 RSS 中 |

因此，“模型文件约 2.2GB”和“日志 Peak Memory 1501MB”并不矛盾，也不能直接互减。前者是磁盘制品，后者必须先确认 Runtime 的统计口径。

## 3. Linux 上怎样测

### 3.1 整机视角

```bash
free -h
cat /proc/meminfo
vmstat 1
```

重点看：

- `MemAvailable` 是否持续下降；
- `si/so` 是否出现持续 swap in/out；
- 运行时是否发生明显 I/O wait；
- 内核日志是否出现 OOM killer。

```bash
dmesg -T | grep -Ei 'oom|out of memory|killed process'
```

### 3.2 进程视角

```bash
cat /proc/<PID>/status
cat /proc/<PID>/smaps_rollup
pmap -x <PID>
```

`smaps_rollup` 重点记录 `Rss`、`Pss`、`Private_*`、`Shared_*`、`Swap`。不要只截一次；应在初始化、Prefill、长 Decode、相机打开和多轮对话后各取样。

### 3.3 设备与连续内存

相机、RGA、显示和 NPU 可能使用 DMA/CMA。检查：

```bash
grep -Ei 'CmaTotal|CmaFree|MemAvailable' /proc/meminfo
```

若 BSP 提供 NPU/ION/dma-buf 调试节点，再记录对应统计。不同内核节点可能不同，文档里必须写明板卡镜像和节点来源，不能照搬别人的路径。

## 4. Qwen3.5-2B 的缓存容量不能按 24 层标准注意力计算

Qwen3.5-2B 是 18 层线性注意力 + 6 层全注意力。若全注意力 KV 用 2 字节保存，其理论容量为：

\[
M_{KV}=2\times6\times T\times2\times256\times2
\]

即约 `12 KiB/token`：

| 上下文 token | 全注意力 KV 理论量 |
|---:|---:|
| 1024 | 12 MiB |
| 2048 | 24 MiB |
| 4096 | 48 MiB |

另外 18 层线性注意力维护递归状态和卷积状态；Runtime 还可能预分配工作区。最终内存必须以板端实测为准，不能只用 KV 公式决定“4096 一定能跑”。详见 [04_Prefill_Decode_混合注意力与缓存](./04_Prefill_Decode_混合注意力与缓存.md)。

## 5. 给本机建立容量账本

不要先填一个看似精确的预算；先逐项测量：

| 阶段 | MemAvailable 最低值 | 目标进程 PSS | CMA Free | Swap | 备注 |
|---|---:|---:|---:|---:|---|
| Ubuntu Desktop 空闲 5 分钟 | TODO | — | TODO | TODO | 关闭更新后测 |
| Qt 空界面 | TODO | TODO | TODO | TODO | 10 寸屏 |
| Qt + IMX415 预览 | TODO | TODO | TODO | TODO | 记录缓冲区数 |
| RKLLM 初始化完成 | TODO | TODO | TODO | TODO | context=2048 |
| RKLLM 长 Prefill | TODO | TODO | TODO | TODO | prompt=1024 |
| RKLLM Decode 256 token | TODO | TODO | TODO | TODO | 记录高水位 |
| RKNN 视觉模型运行 | TODO | TODO | TODO | TODO | 低分辨率支路 |
| 全功能同时运行 | TODO | TODO | TODO | TODO | 产品基准 |

`M_margin` 不能为零。系统还需要应对日志、网络、文件缓存、瞬时缓冲和驱动分配。建议用“全功能连续运行后的最低 MemAvailable + 无持续换页 + 无 OOM”作为余量判断，而不是死记某个百分比。

## 6. 4GB 设备的工程策略

### 6.1 生命周期优先于微小优化

- 非必要时不同时常驻多个大模型；
- 视觉模型按场景启停，避免相机预览就加载所有推理组件；
- LLM 初始化可放在明确的加载页，避免 UI 假死；
- 模型切换采用“卸载旧模型—确认资源释放—加载新模型”的状态机；
- 限制会话历史与最大生成长度，避免不可控增长；
- 日志采用轮转，不把大量输出堆在内存或系统盘。

### 6.2 摄像头内存也要算

单帧近似容量：

\[
M_{frame}=width\times height\times bytes\_per\_pixel
\]

以 3840×2160 为例：

- RGB888 一帧约 23.7 MiB；
- NV12 一帧约 11.9 MiB；
- 再乘以 V4L2 缓冲区数量、预览支路、中间转换和推理输入副本。

因此 IMX415 不应默认把 4K RGB 多份复制给 Qt 和 NPU。产品结构应分成“显示支路”和“低分辨率推理支路”，尽量复用 DMA/RGA 能力并控制队列长度。

### 6.3 Swap 与 zram 的正确角色

- Swap 是 OOM 保险，不是容量扩展的性能方案；
- 若 Decode 时持续 `si/so`，系统会出现严重延迟抖动；
- zram 适合压缩匿名冷页，但会消耗 CPU；
- eMMC swap 还会引入 I/O 延迟和写放大；
- 生产目标应是在主要交互路径中不发生持续换页。

## 7. 三类常见“假内存问题”

### 7.1 page cache 看起来占满

Linux 会利用空闲内存做缓存。判断压力要看 `MemAvailable` 与换页，而不是看到 `free` 很小就断言泄漏。

### 7.2 首次加载后 RSS 不下降

Allocator、Runtime 或 mmap 可能保留地址空间和缓存。要结合 PSS、匿名页、映射文件和下一次复用判断，不能只看 `top`。

### 7.3 Python/Qt 包很大等于运行时很大

磁盘安装体积与进程驻留量不是同一概念。真正比较 PyQt、Qt C++ 或其他框架时，应在同一功能、同一插件、同一场景下比较 PSS 和启动时峰值。

## 8. 稳定性实验

1. 冷启动 20 次，记录初始化成功率和峰值；
2. 连续问答 100 轮，每 10 轮记录 PSS；
3. 2048/4096 上下文 A/B，记录是否预分配和峰值差；
4. 相机预览开关 A/B，记录 CMA、PSS、Decode 速度；
5. Qt 页面来回切换 100 次，观察图像缓冲是否释放；
6. 人为终止生成，确认缓存和状态回收；
7. 运行 1 小时，检查 PSS 是否单调增长。

若内存每轮只升不降，才进入泄漏定位：区分 C++ 堆、Qt 对象、图像队列、Runtime、dma-buf 和日志缓存。

## 9. 验收标准

- 能解释磁盘大小、RSS、PSS、CMA 与 Runtime Peak Memory 的区别；
- 有完整功能场景的容量账本，而不是只测 `llm_demo`；
- 主要交互过程中无持续 swap in/out；
- 长时间运行 PSS 不持续增长；
- 发生内存不足时能指出是哪个阶段、哪个组件和哪类内存。

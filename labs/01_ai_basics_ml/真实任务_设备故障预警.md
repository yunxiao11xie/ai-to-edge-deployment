# 真实任务：端侧设备故障预警原型

## 任务背景

假设一台边缘设备持续采集温度、振动、电流、压力、负载率和累计运行时间。现场希望先做一个轻量级模型，在设备本地判断当前状态是否需要检查：

```text
0：设备状态正常
1：设备可能故障，需要检查
```

本任务使用确定性生成的模拟传感器数据。数据不代表真实设备规律，但完整保留了工程问题中的几个重要约束：

- 故障样本比正常样本少；
- 漏掉一次故障通常比多报一次更危险；
- 不能只看 Accuracy；
- 训练和验证必须使用固定、可复现的数据划分；
- 最终指标必须能从真实预测结果重新计算。

## 你的目标

使用经典机器学习完成一个故障二分类基线，并提交机器可验收的预测证据。

最低要求：

| 指标 | 验收线 |
|---|---:|
| Accuracy | ≥ 0.78 |
| 故障类别 Recall | ≥ 0.70 |
| 故障类别 F1 | ≥ 0.68 |

这些指标只是本教学数据上的完成标准，不应直接用于真实工业项目。

## 固定规则

1. 使用 [`task_data.py`](./task_data.py) 提供的数据；
2. 使用 `test_size=0.2`；
3. 使用 `random_state=42`；
4. 划分时必须使用 `stratify=y`；
5. 预处理只能在训练集上拟合，推荐使用 Pipeline；
6. 不能手工修改标签或预测结果；
7. 必须提交测试集编号和逐样本预测，验收器会重新计算指标。

## 开始任务

复制并修改起始代码：

```bash
python challenge_starter.py
```

建议从下面的基线开始，但模型选择由你决定：

```text
StandardScaler
    ↓
LogisticRegression
```

数据存在类别不均衡，可以思考：

- 是否需要 `class_weight="balanced"`；
- 提高故障 Recall 会对误报造成什么影响；
- Accuracy 很高是否可能只是因为正常样本更多；
- 如果模型部署在低功耗设备上，复杂度和收益是否匹配。

## 必须交付

程序需要生成：

```text
artifacts/challenge_submission.json
```

其中必须包含：

- 模型名称；
- 固定测试集的样本编号；
- 每个测试样本的 0/1 预测；
- Accuracy；
- 故障类别的 Precision、Recall 和 F1；
- 二分类混淆矩阵；
- 至少 80 个中文字符的工程结论。

工程结论至少回答：

1. 当前模型产生了多少次误报和漏报？
2. 对故障预警而言，为什么不能只看 Accuracy？
3. 如果模型将部署到端侧设备，你会优先继续优化精度、速度、内存还是数据质量？为什么？

## 验收

生成提交物后运行：

```bash
python validate.py --challenge artifacts/challenge_submission.json
```

验收器会检查：

- 数据划分是否一致；
- 预测数量和取值是否合法；
- 提交的指标能否从预测结果复算；
- 混淆矩阵是否正确；
- 是否达到基础质量线；
- 是否提交了足够完整的工程结论。

## 分级提示

<details>
<summary>提示 1：模型一直漏报故障</summary>

先观察训练集中的正常/故障样本数量，然后了解分类模型的 `class_weight` 参数。不要直接修改预测结果。

</details>

<details>
<summary>提示 2：如何避免标准化的数据泄漏</summary>

将 `StandardScaler()` 和分类器放进 `make_pipeline()`，再对 Pipeline 调用 `fit()`。这样标准化参数只从训练集学习。

</details>

<details>
<summary>提示 3：一个可尝试的基线</summary>

尝试 `make_pipeline(StandardScaler(), LogisticRegression(max_iter=1000, class_weight="balanced"))`，然后根据混淆矩阵分析代价，而不是只追求最高 Accuracy。

</details>
